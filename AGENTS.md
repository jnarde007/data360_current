# Project architecture

- Pin MTN routing centrally in the orders insert trigger and honor that snapshot in delivery; this covers every purchase channel without rewriting payment RPCs.
- Keep MTN provider management behind Super Admin RPCs with audited, concurrency-aware writes; do not allow client settings to bypass activation safeguards.
- Treat provider-confirmed purchase cost as separate evidence from configured financial cost; incomplete evidence must remain visibly incomplete.
- MTN delivery is controlled by two mutually exclusive toggles (portal02_api_enabled / iget_api_enabled) in mtn_provider_settings; both OFF means manual. MTN iGet reuses the verified AT/Telecel iGet endpoints with the IGET_API_KEY backend secret.
- Put shared pure MTN validation and submission-hold rules under the Edge Functions shared directory and test them from the existing Vitest suite; this avoids duplicating safety policy.
- Resolve iGet submission and polling credentials through the shared iGet configuration helper; MTN's network row belongs to Portal-02 and must never supply iGet's URL or key.- An MTN order pinned to Manual may be re-pinned once, to the currently enabled MTN API provider, only on an authenticated admin Send-to-API and only before any provider submission; the trigger and deliver-order both enforce this so old manual orders can be delivered without bypassing pinning.
- MTN number eligibility checks go through the verify-mtn-number function with a server-side cache; they are advisory and fail open so checkout never depends on the third-party checker.
- Any button that must show a solid brand color has to declare that color with the important modifier plus `!bg-none`; the default button variant applies an unlayered gradient rule that otherwise wins over plain background utilities, so a network or Paystack color silently renders as the brand gradient.
- Developer API requests authenticate only via the developer-api function, which hashes the Bearer key and returns one generic 401 for every failure; identity never comes from caller-supplied IDs.
- Super Agent pricing lives in super_agents/super_agent_settings/super_agent_price_overrides and is applied server-side in place_order via _super_agent_price; ordinary, guest and store pricing paths must stay untouched by it.
- Developer API purchases go only through the service-role-only place_developer_api_order, which claims a per-customer hashed Idempotency-Key and calls place_order in one transaction; immediate (no-grace) processing is a transaction-local setting only that wrapper sets, so website orders keep their grace period.
- Developer API request monitoring is recorded only in the background after the response (api_monitor_record* RPCs, fixed endpoint/outcome labels, hourly counters); it must never delay, fail or block a request, and blocking is impossible until the mode check constraint is deliberately extended with explicit owner approval.
- Website wallet checkout (place_order) trusts only the verified JWT role: authenticated callers must own p_customer_id and are forced to the server price, anon is refused, and only service_role may honour a caller amount or the API immediate flag; keep this so browsers can never set prices, act for others or skip the grace period.
